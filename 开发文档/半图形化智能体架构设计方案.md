# 半图形化智能体架构 · 修改设计方案

> 核心理念：**图形化显示逻辑架构，便于开发；每个模块点开可改代码（半图形化）；具备 harness 全部能力；高度自定义。**
> 日期：2026-08-22

---

## 一、现状与问题

当前画布（工作流）的本质是 **"一个智能体的流水线"**：

- 节点按 `data` 边单向串联，数据从左到右流经各节点，输出结束；
- 节点是黑盒：技能（.skill.py）、协议（.protocol.py）、工具（MCP JSON）都是**独立文件**，画布只能"配置"不能"改代码"；
- 图与代码分离：改逻辑必须切到技能页/协议页/记忆页，画布与代码不联动。

由此产生用户指出的核心矛盾：

> **"如果智能体是用画布的形式，那怎么实现多智能体协同？"**

流水线（数据流）只能表达"依次加工"，表达不了多智能体之间**对话、委托、协商、广播、反馈回环**等动态协作。

---

## 二、设计理念：Graph as Code（图即架构，码即血肉）

| 层 | 是什么 | 用户怎么用 |
|---|---|---|
| **图（Canvas）** | 逻辑架构骨架：谁、做什么、连到谁 | 拖拽搭骨架，一眼看懂整体逻辑 |
| **模块（Module）** | 节点 = 可复用的功能单元 | 点开节点 = 编辑真实代码（.py/.md/.json） |
| **编译（Compiler）** | 图 → Python 引擎代码 | 导出独立 LA 包，图与运行产物同源 |
| **运行时（Runtime）** | 流水线 + 消息调度 + 记忆 + 工具 | 执行、可视化高亮、可中途接管 |

一句话：**拖拽搭骨架，点开写代码，图是代码的图形化视图，代码是图的真实实现。**

---

## 三、节点类型体系升级（半图形化单元）

把 harness 全部能力映射为"模块节点"。每个模块 = 图形属性（表单）+ 代码文件（可编辑）：

| 节点 | 现状 | 升级为 | 可编辑代码 |
|---|---|---|---|
| 智能体（skill） | .skill.py 黑盒 | **Agent 模块**：身份/System Prompt/工具/技能/记忆/协议 | `SYSTEM_PROMPT` + `logic.py` |
| 记忆（memory） | 架构 md | **Memory 模块**：policy/facts/ledger + 读写钩子 | `policy.md` + `memory_hooks.py` |
| 工具（tool） | MCP JSON | **Tool 模块**：可**内联 Python 函数** | `tool.py`（`def run(...)`） |
| 协议（protocol） | .protocol.py | **Protocol 模块** | `protocol.py` |
| 通信总线（bus） | 连接点+区域 | **Bus 模块**：黑板（共享数据）+ 事件总线（发布/订阅） | `bus.py`（过滤/路由规则） |
| 子智能体（subagent） | 子工作流 | **Agent 引用**（复用其他 Agent 实例） | 引用目标 Agent |
| 输入/输出 | 文本框 | **IO 模块**：会话/文件/HTTP 多来源 | `io.py` |
| 控制流（**新增**） | — | 条件分支 / 循环 / 并行汇聚 / 消息收发 / 定时 | `flow.py` |

**关键变化**：`tool` 从"只能选 MCP"变为"能内联写 Python 函数"，技能/记忆/协议全部可**原地改代码**——这就是半图形化的落点。

## 四、多智能体协同（A2A 图形化）

### 4.1 画布升级为"多智能体交互图"

一个画布 = 多个 Agent 节点 + 协作关系。每个 Agent 节点有：

- **身份**：agent_id、角色描述
- **能力**：挂载的 Tool / Memory / Protocol / 子技能
- **端口**：入（接收消息/数据）、出（发送消息/数据）

### 4.2 连接类型从 1 种扩到 4 种

| 连接 | 语义 | 对应 A2A 概念 |
|---|---|---|
| `data`（现有） | 数据流：上游输出 → 下游输入（流水线） | 任务链 |
| `message`（**新增**） | 消息传递：Agent 之间对话/发送任务（带协议信封） | A2A send/reply |
| `broadcast`（**新增**） | 广播/扇出：一个 Agent 发给多个 Agent 并行处理 | A2A discovery + fan-out |
| `callback`（**新增**） | 回调/反馈：下游处理完回传上游（循环、评审、协商） | A2A task callback |

图形表现：边带类型徽标（`➤ 数据 / ✉ 消息 / 📢 广播 / ↩ 回调`），颜色区分，点击可改类型。

### 4.3 通信总线升级 = 黑板 + 事件总线

- **黑板（Blackboard）**：共享数据区（保留现有 zone 读写权限 + 挂接式连接点），多 Agent 可读/写同一份上下文；
- **事件总线（Event Bus）**：发布/订阅机制——Agent 发布事件（如 `任务完成`），其他 Agent 订阅后自动响应；
- 总线从"管道"升级为"协作中枢"，天然支撑主管-工人、协商、评审等模式。

### 4.4 协同模式预设（模板一键生成）

| 模板 | 结构 | 典型用途 |
|---|---|---|
| **主管-工人** | 主管 Agent（bus 黑板 + broadcast）→ N 个工人 → 汇总 | 任务拆分并行执行 |
| **评审回环** | 生成 Agent → 评审 Agent → callback 反馈 → 生成 Agent（循环） | 质量把关、迭代 |
| **协商/辩论** | N 个 Agent 通过 message 边轮流发言（循环） | 多视角决策 |
| **流水线** | data 边顺序（现有） | 数据加工链 |
| **RAG 管道** | 输入 → 检索(工具) → 记忆 → Agent → 输出 | 知识问答 |

## 五、半图形化编辑（模块可改代码）

1. **双击模块 = 打开代码编辑器**（复用现有 CodeEditor）：
   - 图形属性表单（左侧） ↔ 代码文件（右侧），双向同步：
     - 改表单 → 生成/更新代码片段（如 System Prompt → `SYSTEM_PROMPT` 区段）
     - 改代码 → 回读元信息（如 `# prompt:` 注释行 → 表单字段）
2. **图 ↔ 代码互转**：
   - 导出：画布 → Python 引擎（现有 engine.py 扩展协同运行时）→ 独立 LA 包
   - 导入（二期）：已有 Python 骨架 → 自动识别为模块图
3. **运行可视化**：执行中节点高亮 + 边动态流动 + 输入/输出气泡（现有节点状态扩展）

## 六、harness 全能力对齐

| 能力 | 在图中如何体现 |
|---|---|
| 会话 | 会话目标 = 某个 Agent 节点或整个图；运行中可交互（提问/接管） |
| 记忆 | 每个 Agent 可挂 Memory 模块 → 多记忆空间共存；记忆读写即节点连线 |
| 工作区 | 模块通过 `read_file`/`write_file` 工具读写工作区沙盒（已有） |
| MCP/工具 | Tool 模块 = MCP 工具图形化 + 内联 Python 函数 |
| 协议/A2A | Protocol 模块约束 message 边的信封与安全（身份/黑白名单/审计） |
| 团队协作 | 图本身可多人共同编辑（已有 team 局域网服务） |
| 导出 | 图 → LA 包 → 独立 exe（已有 exporter） |

## 七、分层架构

```
┌─────────────────────────────────────────────┐
│ 图形层 Canvas      拖拽/连线/缩放/属性表单/边类型  │
├─────────────────────────────────────────────┤
│ 模型层 Graph JSON   {nodes, edges, modules}    │
│                    (workflows/*.json 扩展)     │
├─────────────────────────────────────────────┤
│ 编译层 Compiler    图 → Python 引擎代码          │
│                    (含 message/broadcast/回调调度)│
├─────────────────────────────────────────────┤
│ 运行时 Runtime     流水线 + 事件/消息调度 + 记忆    │
│                    + 工具 + 交互                │
└─────────────────────────────────────────────┘
```

数据模型扩展（兼容旧工作流）：
```json
{
  "nodes": [{
    "id": "ag-1", "type": "agent",
    "module": { "system_prompt": "...", "tools": [...], "memory": "mem-a" }
  }],
  "edges": [{
    "from": "ag-1", "to": "ag-2",
    "type": "message" | "data" | "broadcast" | "callback",
    "protocol": "proto-name"   // 可选，A2A 信封
  }]
}
```

## 八、实施路线（分期）

| 阶段 | 内容 | 验证 |
|---|---|---|
| **P1 协同基础** | 边类型扩展（message/broadcast/callback）；总线黑板+事件；引擎协同调度（消息顺序/并行/回环）；运行可视化 | 主管-工人 + 评审回环模板跑通 |
| **P2 半图形化** | 模块=图形↔代码双向互转；Tool 内联 Python；控制流节点（条件/循环/并行） | 画布内直接改代码运行 |
| **P3 自定义化** | 模板库；自定义模块（新建空白模块→定义端口→成新节点类型）；Python 骨架导入 | 用户自建模块全流程 |

## 九、待确认的关键决策

1. **协同执行模型**：P1 先做"边调度"（按图结构顺序/并行驱动，无消息总线内核），还是直接上"事件驱动运行时"（完整异步，复杂度高）？建议：**先边调度，事件总线做薄层**。
2. **图码互转深度**：双向实时同步 vs 代码为主（图形只读展示架构、代码是唯一真相）？建议：**代码为主、图形双向回读**。
3. **命名统一**：节点"技能"是否统一改叫"智能体"（与需求 1 一致）？工具节点是否并入智能体内部挂载，画布只保留 Agent/记忆/总线/控制流/IO？
