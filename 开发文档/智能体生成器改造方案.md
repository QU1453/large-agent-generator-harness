## 1. 背景与定位

**LAG harness = 大型 Agent 生成器（Large Agent Generator）**。

核心链路：把可视化工作流「编译」成一个自包含的 LA 包，可导出为：

1. **Python 库** —— 外部软件 `import la` 直接调用；
2. **HTTP 服务** —— 启动服务后用 js / 任意 HTTP 客户端调用；
3. **单文件 exe** —— 双击即用，自带极简控制台（PyInstaller 冻结）。

---

## 2. 三大理念（本次改造的总纲）

| 理念 | 落地含义 |
|---|---|
| **便于开发** | 智能体/工作流作者写一个东西的契约统一、编辑体验一致、改一处即生效 |
| **显式开发** | 一切资产与导出的 runtime **都是代码文件**，可见、可改、可版本化、可单测；反对「字符串模板黑盒」与过度图形化 |
| **插件式开发** | 工具 / MCP / 技能 / 协议 / 记忆统一为**插件**，走同一契约 + 注册中心，接新能力不改主流程 |

---

## 3. 现状诊断

| 问题 | 说明 |
|---|---|
| 内核是「拼出来的代码」 | harness 内是 JS 引擎（`electron/workflow.js`），导出物是 Python 引擎（`exporter.js` 模板字符串生成的 `engine.py`），两套语义，会漂移 |
| 导出 runtime 是黑盒 | `exporter.js` 用 `PY_LLM/PY_TOOLS/PY_ENGINE/PY_HTTP/PY_LA` 等 10+ 个 JS 模板字符串内嵌 Python，无法单独调试/版本化/扩展 |
| 工具通道分裂 | 内置工具（`list_dir/read_file/write_file`）、`run_workflow`、`memory_*` 走 `tools.js` 硬编码 switch；MCP 工具走 `mcp.js`，两条通道 |
| 资产契约分散 | 智能体是 `.agent.js/.agent.py` 双引擎、技能是 `.md`、协议是 `.py`、工具是 `.mcp.js/.py`，底层契约字段不一 |
| 记忆画布遗留 | 记忆已改纯文件管理（上一轮），`memcanvas.js` + `canvas.json` + `memory:*canvas*` IPC 成死代码 |

---

## 4. 目标架构

```
┌──────────────────────────────────────────────────────────┐
│  LAG harness（智能体生成器）                                  │
│                                                            │
│  ① 资产层（显式代码文件）   智能体 / 工具(MCP) / 技能 / 协议 / 记忆 │
│  ② 插件层（统一契约）       工具插件 = name+desc+JSONSchema+handler │
│  ③ 注册中心（内部，非UI）   统一索引/发现全部资产                    │
│  ④ 编排层（工作流图）       节点化编排，语义唯一化                    │
│  ⑤ 编译器（导出器）        显式模板工程 → Python库 / HTTP / exe      │
│  ⑥ 产物层（独立可运行）      import la / --serve / 双击 exe        │
└──────────────────────────────────────────────────────────┘
```

## 5. 详细改造清单

### M0 · 导出器内核重构：字符串模板 → 显式模板工程（最高优先级）

| # | 改造项 | 现状 → 改造 | 验收标准 |
|---|---|---|---|
| M0-1 | 拆出**显式模板工程** | 新建 `electron/export-template/`，用真实 `.py` 文件：`la/__init__.py`、`executor/{engine,llm,tools,config,state}.py`、`transports/{cli,http_server}.py`、`web/index.html`、`la_main.py`，用 `{{placeholder}}` 占位；导出时拷贝目录 + 渲染占位 | 模板工程可被 `pytest` 单独测试；`exporter.js` 只做「拷贝 + 渲染」，不再内嵌 Python |
| M0-2 | **图执行语义唯一化** | `workflow.js`（JS）与 `engine.py`（Python）各写一遍拓扑排序 + zone 总线 + A2A + 工具循环；改为一份 `图执行规范` 约束，加对照测试 | 同一工作流在 harness 内与导出物运行结果一致 |
| M0-3 | **导出物版本化 manifest** | `manifest.json` 增加 `schemaVersion`、`assets`（引用的智能体/工具/技能/协议源码快照）、`contract` 强类型 | 旧导出物可被新编译器识别并迁移 |

### M1 · 统一工具插件层 + 组件注册中心

| # | 改造项 | 现状 → 改造 | 验收标准 |
|---|---|---|---|
| M1-1 | **统一工具插件契约** | 定义 `{ name, description, parameters(JSON Schema), handler(ctx,args) }`；所有工具（内置/MCP/记忆/工作流）都实现该契约 | `llm.getToolSchemas` 只剩一个数据源 |
| M1-2 | 内置/记忆/工作流工具**包装成虚拟 MCP 插件** | 把 `tools.js` 的 switch 分支、`memory_*`、`run_workflow` 各封装为插件对象，注册进同一注册表 | 删除 `tools.js` 硬编码 switch；导出物只依赖一份插件注册 |
| M1-3 | **组件注册中心（内部，非 UI）** | 新建 `electron/registry.js`：统一索引 智能体/工具/MCP/技能/协议/工作流；各面板、导出器、工作流节点选择器、A2A 发现都从它读 | 新增一类资产无需改各面板，注册中心自动可见 |
| M1-4 | **MCP 五阶段契约显式化** | `mcp.js` 的「发现→构造→通信→执行→响应」显式建模；支持真实 MCP Server（stdio/HTTP/SSE）接入，保留本地 `.mcp.js/.py` 为「本地插件」快捷形式 | 能接入一个外部 MCP Server 作为工具源 |

### M2 · 资产契约统一 + 智能体 Python 化

| # | 改造项 | 现状 → 改造 | 验收标准 |
|---|---|---|---|
| M2-1 | **智能体单格式（Python）** | 智能体统一为 `.agent.py`（`AGENT_*` 常量 + `system_prompt(ctx)` 函数，工具用 `'mcp:xxx'` 引用）；JS 智能体一次性迁移 | 不再有两套加载引擎；导出物智能体与 harness 内智能体同源码 |
| M2-2 | **统一资产清单** | 每个资产附带轻量描述（名称/描述/分类/版本/作者），由注册中心索引；分类只存一处（代码即事实），废弃「代码字段 + 单独 categories.json」双份维护 | 分类单一数据源 |
| M2-3 | **显式代码编辑器统一** | 所有资产双击进入同一个显式编辑器（智能体/工具/技能/协议/记忆文件/导出模板），补语法高亮 + Ctrl+S + 契约校验反馈 | 编辑任意资产体验一致 |
| M2-4 | 工作流内**右键智能体直接编辑源码** | 已有（`onEditAgent`），确认覆盖 Python 智能体 + 显示契约错误 | 右键→编辑器→改→重载，闭环 |

### M3 · 导出接口契约明确化（产品面）

| # | 改造项 | 现状 → 改造 | 验收标准 |
|---|---|---|---|
| M3-1 | **Python 库接口增强** | 保留 `La.run(message, session_id)`；新增 `La.run_structured()` 返回 `{content, trace, usage}`；`La.config` / `La.data_root` 覆盖 LLM 配置与数据目录 | 外部 `import la` 可同步/结构化调用 |
| M3-2 | **HTTP 契约规范化** | 明确端点：`/v1/run`（同步）、`/v1/run/stream`（SSE）、`/v1/config`、`/v1/health`；输出 OpenAPI/JSON Schema + js 调用示例（fetch/axios） | 前端 js 拿到规范即可对接 |
| M3-3 | **契约强类型化** | `manifest.contract.input/output` 生成 pydantic/dataclass，运行时校验入参出参 | 非法入参在边界被拦截并给清晰错误 |
| M3-4 | **API key 首次配置页 + env 覆盖** | 保持并确认导出物首个对话前弹配置页、`env:LLM_*` 覆盖优先级一致 | 导出物脱离 harness 独立运行、key 不进包 |

### M4 · 横切能力插件化（来自文档，优先级中/低）

| # | 改造项 | 说明 |
|---|---|---|
| M4-1 | 可观测性插件 | 统一 `tracer/logger` 钩子（节点状态/工具调用/token 用量），注入 harness 与导出物 |
| M4-2 | 异常恢复插件 | 重试/降级/回滚钩子，挂到工具与节点执行层 |
| M4-3 | 资源自适应 | 按任务复杂度路由模型（成本/延迟自适应），作为配置项 |
| M4-4 | 记忆三件套进阶 | `policy/ledger/views` 闭环 + 双时态检索（记忆已文件化，此为检索/视图进阶） |

### M5 · 清理遗留（可推翻项）

| # | 清理项 | 说明 |
|---|---|---|
| M5-1 | 废弃 `memcanvas.js` + `memory:*canvas*` IPC + `canvas.json` | 记忆已改纯文件管理，画布后端成死代码 |
| M5-2 | 清理旧 e2e/测试脚本中「记忆画布/画板」断言 | 与 M5-1 配套 |
| M5-3 | 废弃双引擎智能体的 JS 分支 | 随 M2-1 落地后，`agents.js` 只保留 Python 加载 |
| M5-4 | 归整 `.stage-*` 瞬态目录与旧验证脚本 | 无害遗留，归整 |

## 7. 风险与回滚

1. **智能体 Python 化（D1）**：需迁移 `data/agents/*.agent.js`（内置 assistant/coder/reviewer/researcher/writer 等）。迁移后保留 `.agent.js` 源文件一份备份，界面优先加载 `.agent.py`；回归「智能体重载 / 会话选择 / 工作流节点」全链路。
2. **导出器重构（D2）**：新模板工程与旧字符串模板并行一段时间，`exporter.run` 默认走新模板，旧模板保留到 P3 验证通过后删除；用现有导出的 `manifest.json`（如 `订单客服`）做回归对照。
3. **插件统一（D3）**：`tools.js` 硬编码 switch 先改造成「注册表 + 分发」，保持函数名（`list_dir/memory_*`）与 schema 不变，避免破坏现有智能体 `AGENT_TOOLS` 引用。
4. **回滚粒度**：每个里程碑独立可验证、独立可回滚；改动集中在 `electron/`，前端只在 M2-3 编辑器统一时改动。

## 8. 验收口径

- **P0**：`export-template/` 可 `pytest` 通过；导出物与 harness 内运行同一工作流结果一致（对照测试）；`npm run build` + 打包 release 成功。
- **P1**：`llm.getToolSchemas` 单一数据源；删除 `tools.js` 硬编码 switch；新增一类工具无需改各面板即自动可见。
- **P2**：智能体只剩 `.agent.py` 一种格式；分类单一数据源；任意资产双击编辑体验一致。
- **P3**：`import la` 同步/结构化调用可用；HTTP 五端点 + OpenAPI + js 示例可用；契约强类型校验生效。
- **P4**：可观测/异常恢复/资源自适应以插件形式可挂载、可禁用。
