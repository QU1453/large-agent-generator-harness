# 工程能力开放到工作流（方案）

> 依据：8/20 开发文档"harness 工程（讨论方案）：上下文工程 / 工具编排 / 验证机制 / 状态管理 / 可观测性 / 人类接管"
> 状态：**方案草案**。目标：把 harness 内置的工程能力从"黑盒"变为工作流里可自定义的一等公民，且随工作流一起导出、独立运行。

---

## 一、目标与总原则

**目标**：六类工程能力全部可在工作流中自定义——可拖入、可连接、可配置、可随导出物固化。

**三条底线**：
1. **默认行为不变**：不配置任何能力时，工作流运行行为与现在完全一致（向后兼容）；
2. **随导出固化**：所有自定义都烘焙进 LA 包（manifest/引擎），脱离 harness 独立运行；
3. **人可读可改**：自定义结果落为可读文件（节点/配置都在工作流 JSON 与导出物里可见）。

---

## 二、核心判断：纵切 vs 横切

能力开放的最大坑是**形态选错**。六类能力分两类：

| 形态 | 定义 | 适合的开放方式 |
|------|------|----------------|
| **纵切（流水线内）** | 是"流中的一步"，有输入/输出 | **节点化**：新增节点类型，复用画布/连线/引擎 |
| **横切（全局行为）** | 作用于整个运行过程，无固定位置 | **配置化**：工作流级设置面板，引擎按配置生效 |

分类结果：

| 能力 | 形态 | 开放方式 |
|------|------|----------|
| 工具编排 | 纵切 | 节点化（分支/循环/并行） |
| 验证机制 | 纵切 | 节点化（校验/断言节点） |
| 人类接管 | 纵切 | 节点化（人工确认节点） |
| 上下文管理 | 横切为主 | 配置化（区域总线保留节点形式，压缩/注入规则走配置） |
| 状态管理 | 横切 | 配置化（会话/记忆作用域、持久化开关） |
| 可观测性 | 横切 | 配置化（日志/追踪/回调目标）+ 节点挂钩点 |

---

## 三、六类能力分述

### 1. 工具编排（节点化，阶段二）

现状：节点链接工具/技能（已实现）、子工作流、区域总线、Kahn 拓扑排序、运行期工具注册。

开放项：
- **条件分支节点**：`if/switch`，按上游输出（或表达式结果）路由到不同下游；
- **循环节点**：`for/each`，对集合逐项执行子图（复用子工作流递归）；
- **并行节点**：fan-out/fan-in（同一输入分发多个下游，汇总结果）；
- 自定义"工具适配"：节点上直接写工具调用序列（迷你脚本，可导出为 Python）。

### 2. 上下文管理（横切配置 + 区域总线，阶段三）

现状：区域总线 `[[区域]] ... [[/区域]]` 读写权限（节点级 readZones/writeZones，已实现）；无压缩/窗口策略。

开放项：
- **上下文策略（工作流设置）**：最大 token 预算、摘要压缩阈值、滑窗长度；
- **注入规则**：工作流级"全局注入"（固定指令/知识片段自动注入所有智能体节点，类似技能但作用域更大）；
- 区域总线增强：区域嵌套、区域引用（一个区域可引用另一区域）、区域持久化（跨会话保留）。

### 3. 验证机制（节点化，阶段一）

现状：仅编译期校验（checkWorkflow：智能体存在、工具引用、技能存在）。

开放项：
- **校验节点**：对上游结果做断言（正则/包含/JSON Schema/调用一个校验工具），失败可"重试 N 次"或"终止并报错"或"走失败分支"；
- **格式转换节点**：上游文本 → JSON/CSV/Markdown 结构化输出（为下游工具提供规范输入）；
- 运行期导出校验增强：校验节点定义随导出固化。

### 4. 状态管理（横切配置，阶段三）

现状：会话/记忆空间（memory/ 骨架）、工作流运行期会话。

开放项：
- **状态作用域配置**：全局（跨会话）/会话（同会话多轮）/单次运行；
- **记忆绑定**：工作流级选择"记忆策略"（关联 M3 记忆 MVP 的 policy）；
- 状态查看：运行时可读"当前状态面板"（内存、区域、已写记忆）。

> **记忆管理归属（答疑）**：记忆**不做成工作流节点**，也不放进画布——它是**横切能力**，走工作流级配置：
> 每个工作流可选一套"记忆策略（policy）"，由 M3 记忆 MVP 提供（`memory_*` 工具 + md 持久化 +
> 会话三件套），策略决定哪些智能体节点/区域读写哪块记忆（如"任务记录→全局记忆、中间产物→会话记忆"）。
> 它作为**独立里程碑（M3）**推进，与阶段三的"上下文策略"复用同一策略引擎，二者衔接而非互相替代。
> 底线不变：不配置记忆策略 = 现有记忆行为完全不变。
>
> **已落地（本轮 MVP）**：节点级记忆链接——智能体/输入/输出节点可在框内「🧠 记忆」组链接记忆架构
> （`data/memory/<name>.md`），运行时获得 `memory_read/write/append` 工具并随导出固化（engine.py
> `_bind_memory`）。工作流级"记忆策略"（policy 选择/作用域）仍留待阶段三与 M3 合并推进。

### 5. 可观测性（横切配置 + 挂钩点，阶段三）

现状：节点 trace（工具调用/节点进度）、前端运行转圈指示。

开放项：
- **工作流设置**：日志级别、是否记录输入输出全文、回调 URL（每个节点事件 POST 出去，方便外部监控）；
- **节点挂钩点**：任意节点可选"日志标签"，trace 按标签分组；
- 导出物同享：LA 包日志写 `data/logs/`，可开关。

### 6. 人类接管（节点化，阶段一）

现状：无。

开放项：
- **人工确认节点**：运行到该节点时暂停，等待人在界面确认/修改内容后再继续（前端弹确认卡，导出物 web 控制台同步支持）；
- **人工输入节点**：暂停等待人提供额外输入（区别于工作流输入节点的静态文本）；
- 超时策略：N 分钟未确认则跳过/中止（可配置）。

## 四、实施路线

| 阶段 | 内容 | 依赖 | 形态 |
|------|------|------|------|
| **阶段一 · 纵切验证** | 校验节点（断言/重试/失败分支）；人工确认节点 + 人工输入节点 | 无（复用现有节点/连线/引擎/导出） | 节点化 |
| **阶段二 · 编排增强** | 条件分支、循环、并行节点 | 阶段一（子工作流递归已有） | 节点化 |
| **阶段三 · 横切配置** | 上下文策略、状态作用域、可观测设置、区域增强 | 阶段一/二 + M3 记忆 MVP | 配置化 |

每阶段同步：WorkflowPanel（画布/菜单/设置页）→ workflow.js（引擎）→ exporter.js（checkWorkflow/buildManifest/PY_ENGINE）→ e2e 验证。

---

## 五、风险与对策

| 风险 | 对策 |
|------|------|
| 画布滑向"编程语言"，门槛上升 | 每个开放能力带默认行为；文档/示例工作流；节点参数尽量下拉/填空而非写代码 |
| 横切能力硬塞节点导致语义混乱 | 严格执行"纵切节点化、横切配置化"分类 |
| 调试成本上升 | 阶段三的可观测性前置，自举：先有日志/追踪再开放复杂能力 |
| 导出复杂度失控 | 每个能力导出前过 checkWorkflow；导出物保持"运行期薄" |

## 六、待决策点

1. 阶段一先做「校验节点」还是「人工确认节点」，还是两者同时？
2. 条件分支的判定表达式：纯配置（下拉/文本）还是允许写轻量表达式（类 Python 表达式）？
3. 人工确认节点在导出 exe 控制台里的交互形态（卡片按钮 vs 文本输入框）？
4. 上下文策略是否并入 M3 记忆 MVP 一起做（策略引擎复用）？
